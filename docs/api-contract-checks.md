# API contract checks

Pull requests targeting `main` are checked for CRD compatibility by the shared
checks in
[`red-hat-data-services/api-contract-tests`](https://github.com/red-hat-data-services/api-contract-tests).
The checks need no cluster and start in **report mode**: findings are shown on
the pull request but do not fail it. They are pull-request jobs, not promotion
gates.

## What is covered

The `crd-contract` job runs the static CRD check on the CRDs generated by
`make manifests`, comparing them with a baseline commit of this repository:

- `config/crd/bases/modelregistry.opendatahub.io_modelregistries.yaml`
- `config/overlays/aihub/components.platform.opendatahub.io_aihubs.yaml`
- `config/overlays/aihub/aihub.opendatahub.io_catalogs.yaml`
- `config/overlays/catalog/aihub.opendatahub.io_catalogs.yaml`

It reports removed CRDs and API versions, served or storage-version changes,
removed schema properties, newly required properties, type changes, enum
narrowing and default changes. It does not replace conversion, admission or
upgrade tests.

The `crd-contract-coverage` job fails (once enforced) when a CRD manifest is not
matched by the glob in `.github/workflows/api-contract.yml`, so a new or moved
CRD cannot silently leave the check. Both jobs run on every pull request
targeting `main`, with no path filter. Kustomize patches are not CRD manifests
and are ignored. The mocked CRDs in `internal/controller/testdata/crd` are test
data and are excluded.

## Baseline

The baseline is the commit named in `.github/workflows/api-contract.yml`
(`baseline-refs`), currently the `v0.3.17` release. There should be no breaking
API change within a major version, so moving the baseline forward is an
exception that needs reviewer approval. It must be a full commit SHA; branch
names, tags and `HEAD` are rejected.

## Run it locally

Use the same api-contract-tests ref as the workflow (the `latest` tag), so local
results match CI; fetch the tags again before each run, since `latest` moves to
each new release. The coverage command uses `--report-only` to match the report
mode used in CI; drop it to see the result enforce mode would give.

```sh
git clone git@github.com:red-hat-data-services/api-contract-tests.git ../api-contract-tests
git -C ../api-contract-tests fetch --tags --force
git -C ../api-contract-tests checkout --detach latest
python3 -m pip install PyYAML==6.0.3

baseline=86198eeb141169591f5ad3f6b294471f32456dab   # v0.3.17, as in the workflow
python3 ../api-contract-tests/cmd/contract-tests/cli.py crd-check \
  --repo . --crd-glob 'config/*opendatahub.io_*.yaml' \
  --baseline-ref "$baseline" --output-dir /tmp/crd-contract-report

YQ=/path/to/yq-4.45.1 python3 ../api-contract-tests/cmd/contract-tests/cli.py coverage \
  --repo . --crd-glob 'config/*opendatahub.io_*.yaml' \
  --crd-exclude 'internal/controller/testdata/crd/*' \
  --report-only
```

For `crd-check`, read `report.json.status` in the output directory, not only the
exit code: report mode exits `0` even when breaking findings are recorded.
`coverage` writes no report file; it prints each CRD manifest's status and ends
with `Result: complete` or a list of gaps. With `--report-only` it exits `0` even
when there are gaps, so read that output (or add `--json-output <file>` for a
machine-readable result).
